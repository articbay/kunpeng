## 对现有数据库的影响

迁移链切换以兼容既有生产结构为前提，不通过重建、清空或删除业务表完成。`c3f1a9e7b2d4` 负责把既有数据库安全接入 v3 后续迁移。

后续迁移均为增量变更：新增授权关系、ODS/DWD 表或为现有 Ozon 退货表增加字段。任何环境执行前仍应按发布流程备份并使用 `scripts/release.sh`，不得手工删除旧表或跳过迁移链。

## 日常使用

使用方式不变：

```powershell
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic heads
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "描述"
```

所有新迁移会自动写入 `migrations/versions_v3`。

### Head 验证

以 `alembic.ini` 的 `version_locations` 和 `.py` 迁移源码为准。当前预期唯一 Head 为 `7d1c5e8a9b20`。`__pycache__` 不是迁移源码，不应被提交或作为正式 revision 依据。

## 新环境部署

对全新的空 MySQL 数据库执行：

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

基线会从零创建当前模型注册的全部表。数据库独有且没有模型的历史旧表不会在全新环境中创建；如果其中某张表仍有正式业务用途，应先为它补充模型，再新增正式迁移。

## 临时空库验证

`migrations/env.py` 支持通过 `ALEMBIC_DATABASE_NAME` 临时切换 localhost 数据库名称，不需要修改 `.env` 或输出数据库密码。该覆盖只允许 `localhost`、`127.0.0.1` 或 `::1`。

正常开发和部署不得重复执行旧版基线采用脚本，也不得手工修改 `alembic_version`。生产发布统一通过 `scripts/release.sh`。
