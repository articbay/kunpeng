# 鲲鹏项目快速启动与同步验收 SOP

> 适用范围：Windows 本地测试环境、测试数据库、Wildberries（WB）与 Ozon 真实 API。
>
> 本文整理自一次实际启动和排查过程，面向不熟悉代码的维护人员。文中不包含任何 Token、密码或真实店铺敏感信息。

## 1. 目标与完成标准

本 SOP 的目标是跑通以下链路：

```text
前端页面 → 后端 API → 测试数据库
                         ↑
WB / Ozon API → 独立任务调度器
```

启动成功不等于全流程通过。完整通过至少要同时满足：

- 前端页面可以访问；
- 后端健康检查和 API 文档可以访问；
- 独立调度器只启动一个实例，并注册 47 个任务；
- 调度任务真实调用平台 API；
- API 成功后数据提交到测试数据库；
- 前端重新查询后可以展示数据库中的新数据；
- 关键任务重复执行不会产生重复数据；
- WB、Ozon 的限流或异常任务得到确认和处理。

## 2. 启动前检查

### 2.1 需要准备的程序

- Python 和项目指定的 Poetry 环境；
- Node.js 与 npm；
- MySQL 测试库；
- Navicat（用于人工查看测试库，可选）；
- 已填写本地 `.env`，包含测试库连接和店铺 API 凭证。

不要把 `.env`、Token、Client ID、数据库密码复制到文档、代码、截图或聊天中。

### 2.2 确认目录

后端目录：

```powershell
cd "D:\Work Space\kunpeng_server"
```

前端目录：

```powershell
cd "D:\Work Space\kunpeng_client"
```

### 2.3 首次运行才需要执行

安装后端依赖：

```powershell
cd "D:\Work Space\kunpeng_server"
poetry install
```

应用数据库迁移：

```powershell
poetry run alembic upgrade head
```

安装前端依赖：

```powershell
cd "D:\Work Space\kunpeng_client"
npm install
```

以上步骤不是每次启动都要执行。只有首次安装、依赖变化或新增数据库迁移时才需要重新执行。

## 3. 用三个终端启动项目

三个终端应分别运行前端、后端和独立调度器。不要在同一个终端中依次执行，因为常驻程序会一直占用当前终端。

### 3.1 终端一：启动后端 API

```powershell
cd "D:\Work Space\kunpeng_server"
poetry run uvicorn kunpeng.main:app --reload
```

命令解释：

- `poetry run`：使用项目指定的 Python 虚拟环境；
- `uvicorn`：启动 FastAPI 后端服务；
- `kunpeng.main:app`：加载项目的 FastAPI 应用；
- `--reload`：开发环境修改代码后自动重启。

验证地址：

- 健康检查：<http://127.0.0.1:8000/health>
- Swagger API 文档：<http://127.0.0.1:8000/docs>

健康检查返回 HTTP 200，表示后端已经可以接收请求。

### 3.2 终端二：启动前端

```powershell
cd "D:\Work Space\kunpeng_client"
npm run dev
```

命令解释：

- `npm run dev`：运行 `package.json` 中配置的 Vite 开发服务器；
- 默认访问地址通常为 <http://localhost:5173>；
- 终端最终显示的 `Local` 地址优先于本文示例。

能打开页面只证明前端服务启动成功，还需要登录并确认页面能从后端读取数据。

### 3.3 终端三：启动独立任务调度器

```powershell
cd "D:\Work Space\kunpeng_server"
poetry run python -m kunpeng.scheduler_main
```
实际使用：.\.venv\Scripts\python.exe -m kunpeng.scheduler_main

命令解释：

- `python -m`：按 Python 模块方式运行代码；
- `kunpeng.scheduler_main`：启动当前项目的独立调度入口；
- 该入口会启动 APScheduler，注册 WB 和 Ozon 任务，然后常驻等待触发时间。

正常启动时应看到类似日志：

```text
[调度进程] 启动调度器...
[调度进程] 注册定时任务...
[调度进程] 已注册 47 个任务，进入常驻等待
```

### 3.4 README 中两个调度命令的区别

README 目前同时保留了以下两个命令：

```powershell
poetry run python scripts/run_scheduler.py
poetry run python -m kunpeng.scheduler_main
```

当前项目应使用第二个命令：

```powershell
poetry run python -m kunpeng.scheduler_main
```

原因是当前的47个 WB/Ozon 任务由 `scheduler_main` 显式注册。旧的 `scripts/run_scheduler.py` 只启动调度器本身，可能出现“进程在运行，但没有注册业务任务”的情况。

## 4. 47 个调度任务会做什么

调度器共注册 47 个任务，其中 WB 34 个、Ozon 13 个。详细逐项清单以 `docs/SCHEDULED_JOBS.md` 为准；这里保留面向日常验收的业务分类。

### 4.1 WB 任务

每60分钟运行：

- 销售；
- 订单；
- 评价；
- 问答；
- 退货；
- Marketplace 订单；
- 待处理的新订单。

固定时间运行：

| 平台业务时间 | 任务 |
|---|---|
| 每天 02:00 | 广告活动 |
| 每天 04:00 | 销售漏斗 |
| 每天 08:00 | 余额 |
| 每天 09:00 | 财务数据（T-1） |
| 每小时第 05 分钟 | 广告小时统计、搜索词小时统计 |

### 4.2 Ozon 任务

每60分钟运行：

- FBS 订单；
- FBO 订单；
- 未履约订单；
- 退货；
- 评论。

固定时间运行：

| 平台业务时间 | 任务 |
|---|---|
| 每天 03:00 | 财务数据 |
| 每天 04:00 | 应计类型 |
| 每天 04:30 | 商品信息 |
| 每天 04:45 | 商品中文名称回填（复用翻译缓存） |
| 每天 05:00 | 广告数据 |
| 每天 05:30 | 广告 SKU 明细 |
| 每天 07:00 | 经营分析 SKU 日数据及销售漏斗 DWD |
| 每小时第 10 分钟 | 广告 SKU 小时明细 |

调度器使用配置项 `PLATFORM_TIMEZONE` 对应的平台业务时区；当前测试配置按莫斯科时区触发。莫斯科时间比北京时间慢5小时，例如莫斯科 05:00 对应北京时间 10:00。

“每60分钟”是从调度器启动或任务下次运行时间计算；固定 Cron 任务则按表中时刻触发。关闭期间错过的任务不能假定会全部自动补跑。

## 5. 如何确认任务正在工作

### 5.1 第一层：确认任务已注册

调度器出现下面的日志，只能证明注册成功：

```text
已注册 47 个任务，进入常驻等待
```

这还不能证明平台 API 成功或数据已经落表。

### 5.2 第二层：确认任务被触发

等待终端出现任务名称、店铺名称或“开始同步”等日志。只有出现实际同步日志，才能证明任务已经到达触发时间。

### 5.3 第三层：确认 API 调用成功

重点观察：

```text
响应状态码: 200
同步完成
写入 N 条
```

HTTP 200 表示该次接口请求成功，但仍需要继续确认数据库写入。

### 5.4 第四层：确认数据库提交

日志出现 `COMMIT` 或明确的“写入完成”后，再到 Navicat 查看对应表。

不要仅依赖 Navicat 左侧“表对象”的估算行数。MySQL InnoDB 会缓存表统计信息，左侧可能显示 0，但双击表后仍能看到真实数据。

使用精确 SQL 检查：

```sql
SELECT COUNT(*) AS total
FROM ods_wb_supplier_orders;
```

如果表中有 `create_time` 和 `update_time`，可以进一步检查最新写入时间：

```sql
SELECT
    COUNT(*) AS total,
    MAX(create_time) AS latest_create,
    MAX(update_time) AS latest_update
FROM ods_wb_supplier_orders;
```

检查其他任务时，把表名替换成对应的测试表。还应确认 `shop_id`、业务日期和数据内容属于预期测试店铺。

### 5.5 第五层：确认前端展示

后端 API 每次查询数据库后，前端需要重新发起请求才能看到新数据。当前仪表盘会在以下情况重新加载：

- 第一次进入仪表盘；
- 修改平台或日期筛选；
- 点击页面上的刷新按钮。

因此“数据库已经更新，但页面还是旧数据”时，先点击刷新按钮，不需要重启三个终端。

## 6. 遇到 429 限流怎么办

`429 Too Many Requests` 表示平台拒绝了过于频繁或并发的请求，不是数据库故障。

### 6.1 Ozon Performance 的已知表现

测试中出现过：

```text
活跃报表额度已满（最大 1）
```

当前代码会：

1. 等待报表额度释放；
2. 每隔一段时间重试；
3. 最多等待约600秒；
4. 批量方式失败后回退为逐个处理。

偶发429可以先观察，不必立刻关闭程序。但如果等待结束后仍没有“同步完成”和实际落表，就不能认为该任务成功。

本次验证时，下列 Ozon 广告表仍为 0 行，因此广告链路尚未验收通过：

- `ods_ozon_adv_campaigns`；
- `ods_ozon_adv_stats_daily`；
- `ods_ozon_adv_stats_product_daily`；
- `ods_ozon_adv_stats_product_hourly`。

### 6.2 WB 的已知表现

如果多个测试店铺配置了相同 Token，它们可能共享平台限流额度并互相影响。连续出现429时，应检查店铺凭证是否确实属于不同店铺，或者后续统一做账户级限流，不能简单提高重试频率。

### 6.3 不建议的处理方法

- 不要因为429反复启动多个调度器；
- 不要把所有任务都改成每5分钟执行；
- 不要频繁手工触发同一个耗时报表任务；
- 不要在日志、截图或聊天中展示完整 Token。

## 7. 三个终端能否关闭

| 关闭对象 | 影响 |
|---|---|
| 前端终端 | 页面停止访问，不影响独立调度器继续同步 |
| 后端终端 | API 和 Swagger 停止，前端不能查询数据；独立调度器通常仍可运行 |
| 调度器终端 | 后续定时任务停止，当前正在执行的同步也会被中断 |
| 全部关闭 | 本地项目停止运行，不再自动同步 |

已经 `COMMIT` 到数据库的数据不会因为关闭终端而消失。正在执行但尚未提交的数据不能保证保留。

Poetry 可能显示一个包装进程和一个实际 Python 子进程；Uvicorn 的 `--reload` 也会产生监控进程和工作子进程。这些属于正常结构，不代表启动了两个调度器。是否重复启动应以完整命令行和监听端口综合判断。

## 8. 本次测试已经验证的结果

截至 2026-07-21，本地测试过程已经确认：

- 前端地址返回 HTTP 200；
- 后端 `/health` 返回 HTTP 200；
- 仅有一套独立调度器，包装进程和子进程属于同一次启动；
- 调度器成功注册 47 个任务；
- 调度器实际调用过 WB 与 Ozon 真实 API；
- 部分请求返回 HTTP 200，并产生数据库事务提交；
- 测试库已有 WB 销售、订单、漏斗、广告以及 Ozon 订单、退货、评论等数据；
- Navicat 表对象显示0行的问题是 InnoDB 统计信息缓存，不代表表中没有数据；
- Ozon 广告任务受到“最多一个活动报表”的429限制，尚未完成全链路验收。

上述结果是当时的状态快照，不应当作为未来行数固定不变的断言。

## 10. 每次启动后的快速验收清单

按下面顺序操作，可以避免漏查：

1. 启动后端，访问 `/health`，确认 HTTP 200；
2. 启动前端，打开终端显示的本地地址；
3. 启动独立调度器，确认注册47个任务；
4. 确认没有重复打开第二个调度器终端；
5. 等待一个小时任务实际触发；
6. 在日志中确认 API 状态码、同步结果和数据库提交；
7. 在 Navicat 用 `COUNT(*)` 和最新时间查询对应表；
8. 回到前端点击刷新，确认页面数据变化；
9. 将所有429、401、异常堆栈和0行任务记录下来；
10. 只有24项任务都至少成功一次，且前端查询正确，才标记“全流程通过”。

## 11. 常见问题速查

### 已注册47个任务，但终端暂时没有新日志

调度器正在等待下一个触发时间，属于正常情况。根据任务类型等待每小时触发点或每日 Cron 时间。

### Navicat 左侧显示0行，但打开表能看到数据

这是 InnoDB 的估算统计信息没有及时刷新。以 `SELECT COUNT(*)` 的精确结果为准，不需要每次同步后人工刷新统计信息。

### 数据库有新数据，但前端没变化

先点击仪表盘刷新按钮，或重新进入页面。当前页面不是数据库变化后自动推送更新。

### 调度器出现429，还要不要管

偶发429先观察自动重试；如果最终出现成功日志并落表，可以记录为恢复成功。如果持续失败、超过等待上限或对应表仍为0，则必须作为未通过项处理。

### 关闭调度器后再启动，会自动补齐停机期间的数据吗

不能假定会全部补齐。小时任务通常从重新启动后的调度计划继续运行，具体接口可能通过回看窗口补部分数据，但固定日任务仍应人工检查并在必要时受控补跑。

---

维护原则：先看日志确认任务结果，再看数据库确认落表，最后刷新前端确认展示。三层都通过，才算一次同步真正闭环。
