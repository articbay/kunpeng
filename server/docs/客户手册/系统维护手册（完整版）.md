# 一、从这里开始（总览）

## 你需要知道的 5 件事

1. **AI 帮你改代码，你不用自己写。** 你把想要的功能用大白话说清楚，AI 就会改。
2. **每次改完，AI 会自己做测试。** 项目里已经设好规矩（`AGENTS.md`），AI 改完会自动跑检查，尽量不让它把系统改坏。
3. **改代码 ≠ 上线。** 在你自己电脑上改好、看着没问题后，要执行一条"发布"命令，改动才会真正生效到线上。
4. **出问题能一键回滚。** 万一线上出错，有一条"回滚"命令能立刻退回上一个正常版本。
5. **有些事 AI 也搞不定。** 大改动、疑难故障，别硬扛，见第六章"什么时候该找人"。

## 日常迭代的完整流程（记住这 4 步）

```
第 1 步：提需求   →  第 2 步：AI 改 + 自检  →  第 3 步：本地看效果  →  第 4 步：发布上线
```

1. **提需求**：打开 Codex，套用第三章的提示词模板，把需求填进去发给它。
2. **AI 改 + 自检**：AI 会先告诉你打算怎么改，你说"可以"，它改完会自己跑测试并汇报结果。
3. **本地看效果**：在你自己电脑上启动系统看看对不对（怎么启动见下方"本地预览"）。
4. **发布上线**：确认没问题后，执行发布命令（见第四章）。

## 本地预览（在自己电脑上看效果，不影响线上）

> 第一次用需要装好环境，让 AI 帮你，直接对它说："帮我在本地把项目跑起来，一步步教我。"

启动后用浏览器打开：

- 后端接口文档：http://localhost:8000/docs
- 前端页面：http://localhost:5173

## 遇到看不懂的情况，直接这样问 AI

你不用自己判断，把下面的话原样发给 AI 即可：

- "刚才这段你能用大白话再解释一遍吗？我不懂代码。"
- "这样改会不会有风险？会不会影响现在正常的功能？"
- "你帮我确认一下，改完之后测试都通过了吗？"
- "我现在该做什么？一步步告诉我，我照着做。"

**任何时候拿不准，就先别发布、先别确认，把情况原样告诉 AI，让它解释清楚再决定。** 慢一点没关系，把线上系统改坏了才麻烦。

# 二、需求怎么描述清楚

> AI 不会读心。你说得越具体，它改得越准。下面这套"5 要素"能帮你把需求讲明白。

## 讲需求的 5 个要素

每次提需求，尽量把这 5 点说清楚：

1. **在哪** —— 哪个页面、哪个功能、哪个按钮？（例：数据看板的"导出"按钮）
2. **现状** —— 现在是什么样的？（例：现在导出的是 Excel，只有销量）
3. **想要** —— 你希望变成什么样？（例：导出里再加上广告花费和退货率）
4. **给谁 / 干嘛** —— 谁用、用来做什么？（例：给运营看，每周汇报用）
5. **成功标准** —— 怎样算做对了？（例：导出的表格里能看到这 3 列数据，数字和后台对得上）

## 反面例子 vs 正面例子

❌ 太模糊："帮我把报表弄好看点。"
✅ 清楚："商品列表页的表格，把'库存'这一列移到'价格'右边，并且库存小于 10 的数字标红。"

❌ 太模糊："数据不对，你看看。"
✅ 清楚："销售看板显示今天销量 100，但 Wildberries 后台是 120。我选的日期是今天，店铺是 A 店。数字对不上。"

## 当 AI 理解错了，这样纠正

- "你理解得不对。我的意思是【重新说一遍，换个说法】。"
- "不是这个页面，是【具体位置】。"
- "先别改了，我们退回去。我重新说一下需求：【……】"

## 拿不准需求本身时

直接用第三章的 **模板 7（咨询）**，让 AI 先帮你评估可行性和方案，你看完再决定做不做。别急着让它动手。

## 一个好习惯

改动前，可以先问 AI 一句：
> "开始前先复述一遍你理解的我的需求，我确认没问题你再动手。"

这样能在它动手前就发现理解偏差，省去返工。

# 三、提示词模板（复制 → 填空 → 发给 AI）

> 用法：找到最接近你需求的模板，**复制整段**，把【方括号】里的内容换成你的具体情况，发给 Codex。
> 每个模板结尾都有一句"三板斧"，请务必保留——它能逼 AI 先解释、再动手、自己测试。

## 通用三板斧（所有模板都带，别删）

> 请遵守项目根目录 `AGENTS.md` 的规则。开始前先用一句话复述我的需求并说明你打算怎么改；
> 改完后自己运行测试和检查；最后用大白话告诉我：改了什么、会不会影响现有功能、我下一步该做什么。

## 模板 1：新增一个定时同步任务（定时自动拉平台数据）

```
【加定时同步任务】
我想新增一个定时任务，自动通过 API 同步平台数据。
同步哪个平台：【比如 Wildberries / Ozon】。
同步什么数据：【比如 新订单 / 退货 / 客户评价（客户声音）/ 销售 / 广告花费】(附上文档地址)。
从什么时候开始同步：【比如 立即生效 / 每天服务重启后 / 指定某个时间点开始】。
多久同步一次：【比如 每小时一次 / 每 2 小时一次 / 每天凌晨 3 点】。
每次同步的时间范围：【比如 最近 2 天 / 最近 7 天 / 昨天到今天】。
数据存到哪：【比如 存进已有的某张表 / 新建独立的表，不确定就写"你建议"】。
重复数据怎么处理：【比如 已存在的就更新、不要删除历史；不确定就写"你建议"】。
给谁用、用来干嘛：【比如 供下游智能体查增量、有新订单就飞书提醒】。

注意：这属于会动数据库和调度的需求。请先按 AGENTS.md 给我方案（新建哪张表、调度频率、时间窗口、涉及哪些文件），我确认后再动手；如需改数据库请生成新的迁移，不要删已有迁移。相关说明可参考 docs/SCHEDULED_JOBS.md。
请遵守 AGENTS.md。改完自己跑检查（含数据库迁移测试），最后用大白话告诉我：任务什么时候开始、多久跑一次、每次同步哪段时间的数据、数据存在哪、会不会影响现有数据。
```

## 用模板时的 3 个小提醒

1. **一次只提一个需求。** 别把 5 件事塞进一条消息，AI 容易改乱，也不好验收。
2. **报错信息越全越好。** 有红色文字、截图文字，尽量原样贴给它。
3. **AI 说"做完了"不代表就能上线。** 先在本地看效果，确认对了再发布（见第四章）。

# 四、发布与回滚

> 前提：改动已经在你本地电脑上改好、AI 自检通过、你也在本地看过效果没问题。
> 发布 = 把改动同步到生产服务器并生效。回滚 = 出问题时退回上一个正常版本。

## 发布上线（3 步）

**第 1 步：把代码提交并上传到 Gitee（在你本地电脑操作）**

可以直接让 AI 做，对它说：
> "帮我把这次改动提交并推送到 Gitee，提交信息按项目规范写。"

它会执行类似：
```bash
git add -A
git commit -m "feat(xxx): 本次改动的描述"
git push origin main
```

**第 2 步：登录生产服务器并执行发布脚本**

> 服务器登录方式（IP、账号）由交接时提供，记在第六章的联系信息里。
> 不会登录服务器？让 AI 教你："帮我一步步连接到生产服务器，我用的是 Mac / Windows。"

登录服务器后，执行发布脚本（固定路径，直接复制即可）：
```bash
~/kunpeng/repo/scripts/release.sh
```

脚本会**自动**完成：拉取最新代码 → 新建本次版本目录 → 注入配置 → 备份数据库
→ 构建镜像 → 切换线上到新版本 → 数据库迁移 → 健康检查。
每次发布都会**保留一个独立的版本目录**（在 `~/kunpeng/releases/` 下），线上用 `~/kunpeng/current` 软链指向当前版本，回滚时可秒级切回旧版本。
**任何一步失败会自动停下并把线上切回发布前的版本**，不会带着错误硬上线。

**第 3 步：确认发布成功**

脚本最后会跑一次"体检"（smoke-test）。看到绿色的 ✅ 和"发布完成"就说明成功了。
然后用浏览器打开线上地址，实际点一下你刚改的功能，确认对了。

## 发布后发现线上出问题 → 一键回滚

**别慌，也别急着继续改。** 先回滚到上一个正常版本，让线上先恢复：

```bash
~/kunpeng/current/scripts/rollback.sh
```

它会把线上**秒级切回**上一个版本目录（无需重新构建），并恢复对应的数据库备份。恢复正常后，再把问题原样告诉 AI，让它排查。

## 按版本管理与回滚（进阶）

每次发布都会在服务器 `~/kunpeng/releases/` 下新建一个以时间戳命名的版本目录（保留最近若干个），线上 `~/kunpeng/current` 软链指向当前版本。可以列出历史版本并秒级切回任意一个：

```bash
~/kunpeng/current/scripts/rollback.sh --list                 # 查看所有历史版本（标注当前）
~/kunpeng/current/scripts/rollback.sh 2026.07.14_120000      # 切回指定版本目录
```

在开发机发新版本前，可以先打版本号（CalVer 格式 vYYYY.MM.DD，同日自增序号）：
```bash
./scripts/tag-release.sh
```

## 什么情况必须回滚

- 线上页面打不开、接口报错。
- 核心功能（登录、数据同步、关键报表）用不了。
- 数据明显错乱。

出现以上任何一种，先 `rollback.sh`，再排查。**线上稳定优先。**

## 常见疑问

**Q：发布会不会把数据库里的数据弄丢？**
A：发布前脚本会自动备份数据库；回滚时可恢复。但仍建议重要操作前，让 AI 帮你确认最近的备份文件在不在（在服务器 `backups/` 目录）。

**Q：发布卡住 / 报错看不懂怎么办？**
A：把屏幕上的文字复制下来，发给 AI："发布时报了这个错，帮我看看怎么办：【贴报错】"。搞不定就按第六章找人。

**Q：我只改了文案这种小东西，也要走发布吗？**
A：是的。任何要在线上生效的改动，都要走一次发布流程。

# 五、出问题了怎么办

> 原则：**先让线上恢复正常，再慢慢查原因。** 不确定就先回滚、先问 AI，别自己乱试。

## 第一时间做什么

1. **深呼吸，别乱点。** 记下你刚才做了什么操作。
2. **判断是不是刚发布导致的。** 如果问题出现在你刚发布之后 → 直接回滚（见第四章）。
3. **截图 / 复制报错文字。** 越完整越好，交给 AI。

## 按症状对号入座

### 症状 1：刚发布完，线上就出问题
→ **立即回滚**：
```bash
cd ~/kunpeng_python
./scripts/rollback.sh
```
恢复后把报错发给 AI 排查。

### 症状 2：页面打不开 / 一直转圈
→ 登录服务器，让 AI 帮你查服务状态：
> "线上页面打不开，帮我一步步检查后端服务是不是还在运行。"

常用检查命令（可让 AI 代劳）：
```bash
cd ~/kunpeng_python
docker-compose -f docker-compose.prod.yml ps        # 看容器状态
docker-compose -f docker-compose.prod.yml logs --tail=50 backend   # 看后端日志
```

### 症状 3：数据不对 / 数据没更新
→ 先别改数据库。把具体情况告诉 AI：
> "【某报表】的数据不对，我期望是 X，实际是 Y。帮我先查原因，不要直接改数据库。"

### 症状 4：某个功能报错
→ 用第三章的 **模板 6（修 Bug）**，把报错原文一起贴给 AI。

## 绝对不要做的事

- ❌ 不要自己去数据库里删数据、改数据。
- ❌ 不要在慌乱中反复发布好几个版本（越改越乱）。
- ❌ 不要忽略报错继续操作。
- ❌ 搞不定还硬撑 —— 该找人就找人（见第六章）。

## 把问题讲清楚的模板（发给 AI 或求助时用）

```
【问题描述】
发生了什么：
我做了什么操作才出现的：
是不是刚发布之后出现的：（是 / 否 / 不确定）
报错信息 / 截图文字：
我已经试过：（比如 已经回滚了 / 还没动）
```

# 六、什么时候该找人

> AI + 这套手册能覆盖大部分日常迭代，但有些事非研发确实搞不定。
> 认清边界，该找人时找人，比把系统改坏了再补救省钱得多。

## ✅ 你自己 + AI 能搞定的（放心做）

- 改界面文字、标题、提示语。
- 给已有报表/列表加一个字段、调整显示顺序、加个筛选条件。
- 新增一张基于现有数据的报表或查询页面。
- 调整定时同步的时间和频率。
- 修一些明确的小 Bug（有清晰报错、能复现）。
- 日常发布、回滚、看日志。

## ⚠️ 建议先让 AI 评估、谨慎处理的

- 涉及改数据库表结构的需求（AI 会生成迁移，但要确认过再发布）。
- 一次要改很多地方、牵扯多个功能的需求。
- 对接一个全新的外部平台或新 API。

处理方式：先用第三章的 **模板 7（咨询）** 让 AI 评估，是"大改动"就慎重，或直接找人。

## 🚨 必须找专业研发的（别自己硬来）

- **线上反复出问题、回滚也解决不了。**
- **数据库疑似损坏、数据大面积丢失或错乱。**
- **服务器本身的问题**：磁盘满了、内存爆了、系统崩了、连不上。
- **安全相关**：怀疑被入侵、密钥泄露、异常访问。
- **架构级改造**：性能优化、拆分服务、换数据库、大版本升级。
- **AI 反复尝试都修不好**（改了三四轮还不行，就别再让它试了，容易越改越乱）。

## 找人前，先准备好这些信息

这样能让接手的人快速判断，省时间省钱：

```
1. 出了什么问题（现象 + 截图）
2. 什么时候开始的、是不是某次发布/改动之后
3. 你已经试过什么（有没有回滚、AI 怎么说的）
4. 报错信息原文
5. 最近一次改动内容（git 提交记录，可让 AI 导出）
```

## 联系方式（交接时填写）

- 应急技术支持：__________（建议约定"按次付费"，日常不用花钱，出大事再找）
- 服务器信息：IP __________ / 登录账号 __________（妥善保管，别外泄）
- 代码仓库：https://gitee.com/lingener/kunpeng_python.git
- 数据库备份位置：服务器 `~/kunpeng_python/backups/`

## 一句话总结

**日常小迭代大胆用 AI；碰到数据、服务器、安全、反复修不好的问题，立刻停手找人。**
